# 논문 구현 프로젝트 보고서 — 12주차

소프트웨어및시스템보안 · 12주차 · 구현 진행 및 1차 실행 확인

**논문:** ROPecker: A Generic and Practical Approach for Defending Against ROP Attacks (NDSS 2014)

**팀:** 6조 · **주차:** 12주차 · **작성일:** 2026-11-23 · **사용 AI:** Claude (Anthropic) Opus 5.5(안세진은 Opus 4.8) · **저장소:** github.com/syujin2323/ropecker-trace (코드 기준 main `b2c8705`)

**팀원(역할):** 송유진(팀장, 기반·CLI·비교 실행기), 심형섭(과거 연쇄·통합 판정), 김종훈(gadget DB), 안세진(트레이스 수집), 김수영(윈도·미래 연쇄)

**요약:** 기능 단위 7개의 기본 경로를 main에 병합해 입력(실행 트레이스) → 판정(과거 + 미래 gadget 연쇄 ≥ T=11) → 출력이 이어졌다. 고정 사례 트레이스 6개를 보호 적용 전·후로 실행해 6건 모두 기대와 일치했고, 실제 위반 트레이스는 execve 호출 20스텝 전에 ROP로 판정됐다. Windows 10 PC와 CI 3 OS에서 같은 결과가 재현됐다(Windows 11 PC는 gadget DB 병합 전 단계와 트레이스 수집을 재현).

### 1.2 진행 중이거나 차주로 넘긴 기능

- **임시 구현(stub):** 판정 흐름에는 남지 않았다(6개 결과의 `stubs` 빈 목록). PR #10 병합 전(`e4d8a6b`)에는 윈도·미래 연쇄가 없어 `detector.py`가 윈도 최소 구현과 미래 연쇄 0으로 흐름을 이었다.
- **13주차로 넘김:** jmp·call gadget 에뮬레이션(§V-C, 지금은 ret gadget만 따라가고 jmp·call이나 rsp 변화를 모르는 gadget(`leave` 등)에서 멈춤)과 ROPgadget 교차검증 함수 `compare_ropgadget`(아직 `NotImplementedError`, 판정에 쓰지 않으며 대조는 PR #8에서 함).
- **경계 사례:** 연쇄 길이를 맞춘 합성 트레이스로만 검증했다(실제 입력 트레이스 없음, `pytest` skip 2개, 5.2절 요청 1).

### 1.3 보완된 계획 (11주차 대비 변경과 사유)

- 과거 연쇄는 최근 간접 분기 16개로 한정하고, 11주차 보고서에 적은 jmp 에뮬레이션은 13주차로 미뤘다(사유: 12주차 조교 코멘트 "트레이스 대체 시 최근 분기 16개 제약(§II-B) 참고, ret 연쇄·윈도우부터 우선 연결").
- 정답 연쇄 길이를 담은 합성 트레이스를 사례마다 먼저 만들어 공통 입력으로 썼다(사유: 실제 수집 전에도 각 모듈을 시험).
- 수집기 기반·정상 트레이스는 M0에서 수집 경로(qemu-user gdbstub)를 정한 송유진이 먼저 넣었고(#3), 안세진은 위반 입력 수집과 수집기 개선을 맡았다(#6). 나머지 계획(11주차 4.3-5)은 마쳤다.

## 2. 첫 실행 및 비교 결과

### 2.1 실행 방법과 실행 환경 (README와 같은 명령)

```text
uv sync                 # Python 3.11과 의존성을 uv.lock 그대로 설치
uv run pytest           # 63 passed, 2 skipped
uv run python -m ropecker --trace traces/real/f2-violation.jsonl.gz \
    --window 8192 --threshold 11      # 끝에 --no-check를 붙이면 보호 적용 전
uv run python scripts/run_cases.py    # 고정 사례 6개 전·후 비교 → results/w12/
```

- **환경:** macOS 27.2.1·Windows 10/11·Ubuntu(CI), Python 3.11, capstone 5.0.9, pyelftools 0.33(`uv.lock` 고정). 대상은 gcc 11.4.0으로 다시 빌드한 6주차 `rop_vault`와 glibc 2.35다. Docker는 대상 빌드와 트레이스 수집(qemu-user 7.2·gdb-multiarch 13.1)에만 쓰며, 경로는 저장소 기준 상대 경로다.

### 2.2 고정 검증 사례 3종과 판정 기준 보완

입력·기대 결과는 11주차 재제출본(11/16) 4.5 원문 그대로이고(`cases/frozen.json`, 해시 테스트로 잠금), 모호했던 기준만 코드·출력값으로 정했다(`docs/design.md` 2절).

| 구분 | 입력 (11주차 원문) | 기대 결과 (11주차 원문) | 판정 기준 (12주차 구체화) |
|---|---|---|---|
| 정상 | 6주차 실습 바이너리를 버퍼 크기 미만의 평범한 문자열로 실행한 트레이스 | 미탐지. 판정 "정상", 연쇄 길이 10 이하(T=11 미만), 프로그램 정상 종료 | `verdict` 정상, 연쇄 ≤ 10, 끝 `exit:0` |
| 위반 | 같은 바이너리에서 gadget 17개가 연달아 이어지는 ROP 실행 트레이스 | 탐지. 연쇄 길이가 임계값 11 이상이므로 판정 "ROP", 연쇄를 이룬 gadget 주소 출력 | `verdict` ROP, 연쇄 ≥ 11, `gadgets` 있음 |
| 경계 | 연쇄 길이가 임계값과 정확히 같은 11인 체인, 그리고 10인 체인 | 기준이 "T 이상"이므로 11은 "ROP", 10은 "정상". 한 칸 차이로 판정이 갈리는지 확인 | 11: ROP·연쇄 11, 10: 정상·연쇄 10 |

- **구체화한 점:** 연쇄 길이는 ROP면 처음 ROP가 나온 체크포인트(윈도 밖 코드 페이지 진입·위험 syscall)의 값, 정상이면 최댓값이다(연쇄 = 과거 + 미래, 현재 gadget은 과거에만 셈). "판정"은 `verdict`와 종료 코드(0/1), "정상 종료"는 끝 `exit:0`이다. 적용 전은 `--no-check` 실행 결과, 후는 판정과 멈춘 스텝이며, 실행 결과(`steps`·`trace_end`)와 방어자 판정 로그(`checks`)를 나눠 남긴다.

### 2.3 보호 적용 전·후 실행 결과 비교

6개 트레이스를 같은 조건(W=8192, T=11, 연쇄 ≥ T)에서 전·후 한 번씩 실행했다(`run_cases.py`, 일치는 `pytest`와 같은 판정 함수). 스텝은 0부터 세며, "중단"은 탐지기가 ROP로 판정하고 분석을 멈춘 스텝이다(원논문은 이때 프로세스를 끝냄).

| 구분 | 입력 트레이스 | 보호 적용 전 (`--no-check`) | 보호 적용 후 (탐지) | 기대와 일치 |
|---|---|---|---|---|
| 정상 | 합성 `f1-normal` | 8스텝, 끝 exit:0 | 정상, 연쇄 0 | 일치 |
| 정상 | 실제 `f1-normal` | 9,368스텝, 끝 exit:0 | 정상, 최대 연쇄 1 | 일치 |
| 위반 | 합성 `f2-violation` | 24스텝, 끝 syscall:59 | ROP, 연쇄 17, 스텝 3 중단(execve 스텝 23 전) | 일치 |
| 위반 | 실제 `f2-violation` | 8,443스텝, 끝 syscall:59(execve 호출까지 제어 흐름 탈취) | ROP, 연쇄 18, 스텝 8422 중단(execve 스텝 8442 전) | 일치 |
| 경계 | 합성 `f3-boundary-11` | 18스텝, 끝 max_steps | ROP, 연쇄 11, 스텝 3 중단 | 일치 |
| 경계 | 합성 `f3-boundary-10` | 17스텝, 끝 max_steps | 정상, 연쇄 10 | 일치 |

- **증거 기록:** 그림 1(6건), 그림 2(실제 위반 전·후), 로그·JSON `results/w12/runs/`(예: `f2-violation-real.after.log`). `max_steps`는 합성 경계 트레이스가 체인 뒤 gadget이 아닌 지점에서 기록을 마쳤다는 뜻이다.

### 2.4 판정 로그 예시와 결과 해석

실제 위반 트레이스에 `--verbose`를 붙인 출력(발췌)이다.

```text
판정: ROP (연쇄 길이 18 = 과거 2 + 미래 16, 기준 연쇄 ≥ 11)
체크포인트: 스텝 8422, pc 0x400086c659, 이유 window
  … gadget 18줄, 판정 로그 243줄 중 241줄 생략(스텝 3752만 합 1, 나머지 0)
  스텝    8419  pc 0x4012a5  window      과거 1 + 미래 0 = 1  -
  스텝    8422  pc 0x400086c659  window      과거 2 + 미래 16 = 18  ROP
실행 스텝 8443, 트레이스 종료 syscall:59
```

> 그림 2. 실제 위반 트레이스의 보호 적용 전(--no-check, 종료 코드 0)과 후(ROP, 스텝 8422에서 중단, 종료 코드 1) (캡처는 제출 PDF에 있음)

- **정상·경계:** 6개 모두 입력 → 판정 → 출력이 이어졌고 정상 사례의 오탐은 없었다. 실제 정상의 최대 연쇄 1은 정상 복귀 지점이 gadget 시작 주소와 겹친 경우다(예: 스텝 8419의 `vuln` 끝). 경계는 연쇄 11이 ROP, 10이 정상으로 한 칸 차이에 갈렸다.
- **피해 제거(위반):** 적용 전 실제 위반은 execve("/bin/sh") 호출(스텝 8442)까지 제어 흐름이 탈취됐다(수집기가 이 스텝 직후 대상을 끝내 셸은 뜨지 않음, stdout 끝 `Terminated via GDBstub`). 적용 후에는 20스텝 앞에서 ROP로 판정됐으니, 그때 프로세스를 끝냈다면(원논문 방식) execve는 실행되지 않았을 것이다.
- **연쇄 18과 "gadget 17개":** 페이로드 gadget 17개(ret 14, `pop rdi`·`pop rsi`·`pop rax`)에 더해 `read`가 복귀한 `vuln` 끝 `nop; leave; ret`(0x4012a5)도 gadget 시작 주소라 과거 연쇄에 들어갔다(스텝 8418 `ret` → 8419, 끝의 `ret`까지 실행됨). `docs/design.md`의 과거 연쇄 정의(§II-B·§V-C)대로 센 값이고 기대("11 이상")를 충족해 기대값은 바꾸지 않았다.

### 2.5 원논문과의 차이 메모

- 커널 모듈·page fault·LBR 대신 기록된 트레이스를 분석한다(LBR은 최근 간접 분기 16개로 흉내). 판정은 연쇄 ≥ T(논문은 T 초과, `--cmp gt`로 비교), 미래 연쇄는 ret gadget만, 윈도는 코드 페이지 W/4096개 LRU(논문 8KB), 대상은 x86-64(논문 x86-32)를 qemu-user로 실행한다.

## 5. 막힌 점 및 요청

### 5.1 오류 재현 조건과 시도한 해결 과정

- **수집 결과가 실행마다 달라짐(해결):** 저장소에 넣기 전 첫 수집기(`env -i`·`-seed 1` 없음)로 정상 입력(`collect/inputs/f1-normal.txt`)을 두 번 수집하면 9,364 대 9,368스텝이었다(지금 `collect/run.sh`로는 재현 안 됨). 스텝별 비교로 main 진입 1,747스텝 뒤 `strcmp(argv[1], "main")`의 페이지 경계 분기에서 갈라짐을 찾았다.
  - 원인과 수정: ① 수집기 환경 변수 길이가 argv 주소를 바꿔 분기가 달라짐 → 빈 환경(`env -i`) ② AT_RANDOM(스택 카나리·포인터 가드)이 실행마다 달라 스냅샷이 달라짐 → `qemu -seed 1`. 두 번 수집한 sha256이 같아졌다(`collect/README.md` 재현성, PR #3).
- **위반 입력 수집 중 추적 불안정(해결):** 페이로드가 execve("/bin/sh")를 호출하면 셸이 뜨면서 single-step 추적이 불안정했다(PR #6). 위험 syscall(9·10·25·59) 스텝을 기록한 직후 끝내도록 고쳤고(`collect/gdb_trace.py`의 `RC_STOP_ON_SYS`, 기본 켬), 정상 입력은 영향이 없다(재수집 바이트 동일).
- **미해결(13주차 반례 후보, 구현 버그):** gadget DB에 `loop` 계열이 든 조각이 있다(`asm` 기준 `rop_vault` 7, libc 944, ld-linux 115개). capstone 5.0.9는 loop를 `jump` 그룹에 넣지 않는데 `ropecker/image.py` 62행은 `CS_GRP_JUMP`로만 조건 분기를 거른다(주석의 의도는 loop 포함). 고정 사례 판정에 쓰인 gadget에는 없었다.

### 5.2 조교·교수자 확인 요청 사항

- **요청 1. 경계 사례를 합성 트레이스로 검증해도 되는지:** `uv run python -m ropecker --trace traces/synth/f3-boundary-11.jsonl.gz --window 8192 --threshold 11` → `판정: ROP (연쇄 길이 11 = 과거 1 + 미래 10, 기준 연쇄 ≥ 11)`(종료 코드 1), `f3-boundary-10` → `판정: 정상 (연쇄 길이 10 = 과거 1 + 미래 9, 기준 연쇄 ≥ 11)`(종료 코드 0). 실제 입력이면 `vuln` 끝 +1(2.4절) 때문에 페이로드를 gadget 10·9개로 줄여야 할 것으로 본다. 합성 트레이스 검증을 인정해 주시는지, 실제 입력 트레이스도 필요한지 확인 부탁드립니다.
- **요청 2. 최종 판정 기준:** 같은 명령에 `--cmp gt`(논문 기준 T 초과)를 붙이면 `판정: 정상 (연쇄 길이 11 = 과거 1 + 미래 10, 기준 연쇄 > 11)`(종료 코드 0)이다. 11주차에 고정한 "연쇄 ≥ T"를 주 기준으로 두고, 논문 기준 결과는 최종 보고서에 원논문과의 차이로 함께 보이면 되는지 확인 부탁드립니다.
- **11주차 막힌 점·요청의 처리:** LBR 대체는 코멘트대로 최근 간접 분기 16개로 반영했다. unaligned 포함 DB 생성 시간은 오프셋마다 한 번만 디코드하는 방식으로 libc를 약 50초에 만들고 DB를 커밋해 판정 때는 읽기만 한다(PR #8). 임계값은 논문 실측(§VII-A, 정상 최대 10·공격 최소 17)에 근거한 T=11을 쓰며, 이번 주 실제 정상 트레이스의 최대 연쇄는 1이었다(13주차에 정상 입력을 늘려 다시 잰다).

## 6. 팀원별 기여와 차주(13주차) 계획

11주차 보고서 2절의 12주차 계획(과거 연쇄·통합, gadget DB, 수집기, 윈도·미래 연쇄, 하네스·한 줄 명령)은 모두 결과로 이어졌고, 수집기만 1.3절처럼 나눠 맡았다.

- **13주차 공통(과제 예고):** 고정 사례는 두고 `cases/extra/`에 입력을 더해 반례를 찾고 구현 버그와 명세상 미지원(원논문 한계)으로 나눈다. 후보는 `loop` 포함 조각(구현 버그), jmp gadget에서 끊기는 미래 연쇄(원논문과의 차이), gadget과 겹치는 복귀 지점이다. 14주차 실험 변수는 T(5–17, 11주차 계획)이고, W·판정 비교(≥·>)와 지표(정상 최대 연쇄, 위반 탐지 스텝)는 후보로 두어 13주차에 확정한다.
